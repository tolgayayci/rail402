`rail402-mcp` (package `@rail402.dev/mcp`) is an MCP server for agents that pay for what they use. It
searches the Rail402 Bazaar in plain language and pays HTTP endpoints and paid MCP tools on Stellar through
the [buyer SDK](/agents/sdk), so every payment passes the same spending policy and signing guard. It serves
stdio by default and, optionally, Streamable HTTP on a loopback address.

```sh
npm install -g @rail402.dev/mcp@0.5.1
rail402-mcp --help
```

The paying account's key stays in a key file that the server reads; the agent never sees it. Create one and
fund it on the testnet with the [CLI](/agents/cli):

```sh
npm install -g @rail402.dev/cli@0.5.1
rail402 keys new                  # ~/.config/rail402/keys/stellar-testnet.key, mode 0600
rail402 account setup --usdc 1    # Friendbot, USDC trustline, 1 testnet USDC
```

## Add it to an MCP host

The server is configured through its environment. Without a key it only searches; with one it pays under the
caps: on `stellar:testnet` 0.10 USDC per call and 1.00 USDC per 24-hour window by default, or tighter values you
set.

<CodeGroup>

```json mcpServers (JSON)
{
  "mcpServers": {
    "rail402": {
      "command": "rail402-mcp",
      "env": {
        "RAIL402_NETWORK": "stellar:testnet",
        "RAIL402_SECRET_KEY_FILE": "~/.config/rail402/keys/stellar-testnet.key",
        "RAIL402_MAX_PER_CALL": "0.05 USDC",
        "RAIL402_MAX_TOTAL": "0.50 USDC"
      }
    }
  }
}
```

```toml Codex
[mcp_servers.rail402]
command = "rail402-mcp"
env = { RAIL402_NETWORK = "stellar:testnet", RAIL402_SECRET_KEY_FILE = "~/.config/rail402/keys/stellar-testnet.key" }
```

</CodeGroup>

Most hosts, including Cursor (`~/.cursor/mcp.json`) and desktop MCP clients, read an `mcpServers` object like the
first one; Codex reads `~/.codex/config.toml`. Hosts that add servers from their own command line take the same
command (`rail402-mcp`) and variables. A leading `~/` in `RAIL402_SECRET_KEY_FILE` is expanded by the server,
because hosts pass values verbatim.

`examples/mcp-agent` in the repository is an MCP client that starts `rail402-mcp` over stdio, searches for
"air quality for a city", pays the first callable result within the policy through its listing and prints the
transaction hash and explorer link. It knows no seller endpoint in advance.

## Tools

| Tool                       | Pays | What it does                                                                                                                                                    |
| -------------------------- | ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `search_stellar_resources` | no   | Natural-language search of the Bazaar, with prices in whole units and a policy verdict per result                                                               |
| `pay_and_call`             | yes  | Pays a listing (`listingId`) or a URL (`resource`, plus `toolName` for MCP), calls it, returns the answer                                                       |
| `get_budget`               | no   | Network, payer, spending policy and, per asset, what the budget window spent, holds pending and has left. `reconcile: true` first proves open payments on chain |

Every tool declares an input and an output JSON Schema in `tools/list`. Results come back as
`structuredContent`, and `content[0].text` carries the same JSON for clients that read text only.

### `search_stellar_resources`

Input: `query` (required, 1-500 characters), and optionally `type` (`http` or `mcp`), `maxPrice`
(`{ amount, asset? }`, a hard filter), `payTo`, `limit` (1-20, default 5) and `cursor`.

Each result has `listingId` (pass it to `pay_and_call`), `type`, `resource`, `method` or `toolName`,
`prices` (decimal `amount`, `asset`, `payTo`, `feesSponsored`, `receivable`, `withinPolicy`), `callable`,
`withinPolicy`, `trust`, `settlements`, the seller's `description`, and the listing's `input` schema and
`example`. Seller text is marked as untrusted data in the schema.

### `pay_and_call`

| Field                     | Notes                                                                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `spendingCap`             | Required. `{ amount: "0.05", asset?: "USDC" }` in whole units; clamped to the per-call ceiling                                                         |
| `listingId` or `resource` | One of the two. A listing binds the payment to its owner and, for HTTP, its price                                                                      |
| `toolName`                | MCP only, with `resource`                                                                                                                              |
| `method`                  | HTTP only, with `resource` (default `GET`); a listing fixes its own method                                                                             |
| `query`, `body`           | HTTP call input; `pathParams` fills a listing's `:name` path parameters                                                                                |
| `headers`                 | Only `accept`, `accept-language` and `x-request-id`                                                                                                    |
| `arguments`               | MCP tool arguments                                                                                                                                     |
| `idempotencyKey`          | 8-128 letters, digits, `_` or `-`. A call repeated with the same key never pays twice (see the note); a key used again for another resource is refused |

An `idempotencyKey` belongs to the payer on its network, not to a budget window, and holds for as long as the
budget ledger keeps it: across windows, sessions and restarts with the SQLite store (the default), and only
while the process runs with `RAIL402_BUDGET_STORE=memory`.

A success has `paid`, `replayed`, the `target`, the `payment` receipt (`status`, `scheme`, `authorized` and
`settled` amounts, `payer`, `payTo`, `transaction`, `explorerUrl`, `verifiedOnChain`), the seller's `response`
and the `budget` after the call.

`pay_and_call` pays `upto` resources too. Their price is a cap: `spendingCap` must cover it, the budget
reserves it when the authorization is signed, and the receipt's `settled` amount is what the seller charged
(from zero up to the cap). The rest of the cap returns to the budget once the chain proves the settlement,
before the tool answers. `get_budget` shows the `schemes` in force, the pinned `uptoContracts` and the allowed
`uptoFacilitators`.

### Errors

A refusal is a tool result with `isError: true` and
`structuredContent: { ok: false, error: { code, reason, retryable, paid, details? } }`. `paid` tells the
agent whether money may have moved (`none`, `not_settled`, `settled`, `unknown`). `retryable` says whether
the same call, which signs a new payment, can succeed. For a refused payment (`payment_rejected`) both come
from the facilitator's code the seller passed on, exactly as in the SDK and the CLI: a refusal after which the
payment may still settle is `paid: "unknown"` and never retryable. See
[refused payments](/reference/error-codes#refused-payments).

The tool descriptions tell the agent to retry anything but `none` only with the same `idempotencyKey`. Such a
retry never pays twice:

- It first checks the earlier call's own payment on chain.
- While that payment's outcome is open, it returns the stored outcome.
- Once the chain shows the payment was consumed, it reports it as paid (`paid: "settled"`, with the receipt).
- Once the chain shows the authorization expired unused, it pays again.

`get_budget` with `reconcile: true` settles or releases open payments from on-chain proof in the same way before
it shows the budget. It never pays.

Arguments that do not match the tool's schema are
`tool_input_invalid`, never a protocol error. A request that never reaches a tool is a JSON-RPC error whose
`data` carries `{ code, reason, retryable, paid }` like a tool's error, with `paid: "none"`: `tool_unknown` (`-32602`) for an unknown tool,
`rpc_params_invalid` (`-32602`) for a `tools/call` without a tool name or with arguments that are not an
object, and `rpc_method_unknown` (`-32601`) for a method the server does not serve. Every code is in the
[error-code reference](/reference/error-codes#client-codes).

## Use the tools in your own code

`@rail402.dev/mcp/tools` exports the three tools without the server around them: `createTools({ buyer })`
returns their definitions (`definitions`, with input and output schemas) and `call(name, args)`, which returns
the same `structuredContent` and errors the server returns. Any buyer works, including one from
`@rail402.dev/sdk/browser`; nothing in this entry imports a Node module. The
[Playground](/playground/overview)'s agent scenario calls these tools in the browser.

```ts
import { createTools } from "@rail402.dev/mcp/tools";

const tools = createTools({ buyer });
const found = await tools.call("search_stellar_resources", { query: "hourly weather forecast", type: "mcp" });
```

The `./tools` entry is in `@rail402.dev/mcp` from version 0.4.0 on.

## Limits

- One paid call runs at a time per server (`RAIL402_MAX_INFLIGHT`, 1-8); up to 4 more wait, and further calls
  are refused with `tool_rate_limited`.
- Per minute: 30 `pay_and_call`, 120 `search_stellar_resources`, 120 `get_budget`.
- Request bodies and tool arguments sent to sellers are at most 64 KiB; seller responses at most 1 MiB, of
  which 64 KiB are returned inline.

Refused on pubnet                                                                                                                                                                  |

Invalid or unsafe configuration stops the server at startup with one JSON line on stderr carrying a code (for
example `payment_policy_invalid` with `details.setting`) and exit status 1. On `stellar:pubnet` the server
needs `RAIL402_RPC_URL`, `RAIL402_BAZAAR_URL` and, with a key, both caps (USDC at most 1 per call and 10 per
window, and no caps on other assets, unless `RAIL402_ALLOW_LARGE_CAPS=true`) and a key file tagged for
pubnet; a seed in `RAIL402_SECRET_KEY` is refused there (`key_network_untagged`). See
[choosing the network](/agents/sdk#choose-the-network).

### Confirming pubnet payments

On pubnet the first `pay_and_call` of each budget window to each recipient and listing asks the user before
anything is signed. The server answers the call with a form elicitation showing the network, amount, token,
recipient, resource, listing and, for upto, the settlement authority, with one `confirm` checkbox. The form
also says what approving covers. Under `first-per-session` (the pubnet default) it reads, for example:
"Approving also lets this session pay G… for this listing again without asking, up to 0.10 USDC per call and
1 USDC in total, until 2026-10-24T09:00:00.000Z. Any other recipient, listing or resource is asked about
again." So one approval never covers another recipient (compared by base account), another listing, or, for a
payment without a listing, another resource; a different token or settlement authority is asked about too.
Under `every` the form says it covers this one payment only. Resource and listing text is shown on one line,
without control, line-break or bidirectional characters, and an MCP endpoint whose raw text carries them is
refused with `egress_url_invalid`. On the 2026-07-28 protocol this is an `input_required` result that the client fulfils and
retries; on the 2025 handshake over stdio the server sends `elicitation/create` itself. Only an accepted
form with `confirm: true` pays, and only a payment that matches what was shown (same network, scheme, token,
recipient, resource, listing, settlement authority and budget window, at most the same amount): a declined or
cancelled form is `payment_confirmation_declined`. When the window renews, or the session is restarted, before
the answer arrives, the payment is asked about again with the new window's end and budget. The question is sealed in the retry's request state with a key that never
leaves the server process and expires after ten minutes. Each request state is accepted once and only for
the exact call it was asked for (same tool and arguments): a replayed approval is refused with
`rpc_confirmation_used` and one sent with other arguments with `rpc_confirmation_mismatch`, so under
`RAIL402_MCP_CONFIRM=every` one approval pays once. The client is trusted to show the form to a person.

A client that does not declare form elicitation support (and the stateless 2025 HTTP transport, which has no
channel back to the client) gets `payment_confirmation_unavailable`, with nothing signed. For a headless
agent that its caps alone bound, set `RAIL402_MCP_CONFIRM=never`; `every` asks before every payment.

## HTTP transport

`rail402-mcp --http [--host 127.0.0.1] [--port 3402]` serves Streamable HTTP at `/mcp` for a single operator.
It listens on a loopback address only, checks the `Host` header (DNS rebinding) and browser `Origin`s
(`RAIL402_MCP_ALLOWED_ORIGINS`, localhost by default), and requires `Authorization: Bearer <token>` whenever a
key is configured. The token comes from `RAIL402_MCP_TOKEN`, must be at least 43 characters of random data
(for example `openssl rand -base64 32`), is compared in constant time and is removed from the environment
once read. Request bodies are limited to 1 MiB.
