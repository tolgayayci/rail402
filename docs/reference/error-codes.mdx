Every rejection Rail402 returns carries a stable, machine-readable code and a non-empty, human-readable reason.
Branch on the code; show or log the reason. A specific rejection may replace the default reason below with more
detail, never with an empty string.

- **HTTP status** is the status used when the code is returned as a transport-level error. Verification and
  settlement outcomes are always HTTP 200, as the x402 specification requires.
- **Retryable** says whether sending the same request again, unchanged, can succeed later: after a delay, once
  a balance or trustline changes, or when capacity frees up. A code that is not retryable needs a different
  request, usually a newly signed payment.

Codes are stable. A code is never renamed or removed, and its HTTP status and retryability never change,
without an entry in the changelog; the test suite pins all three for every code. Reasons may be reworded.

The [verification rules](/verification-rules) explain when each facilitator and cataloging code is returned and
which test covers it.

## Client codes

The SDK (`@rail402.dev/sdk`), the seller helpers, the MCP server (`rail402-mcp`) and the CLI (`rail402`) raise
their own codes on the caller's side. The service never returns them. They share the fields above and add two:

- **Paid** says whether money may have moved when the code was raised: `none` (nothing was signed, or the
  signed payment never reached the seller), `not_settled` (the seller or facilitator refused the payment),
  `settled` (the payment settled, then the resource failed) or `unknown` (a payment was sent and its outcome is
  not known yet; the budget keeps it pending until it is proven on chain or its authorization expires). The
  value on an error is authoritative; the table shows the default.
- **CLI exit** is the exit status `rail402` uses when it reports the code. See the
  [CLI reference](/agents/cli#exit-statuses).

Do not simply repeat a call whose error says `settled` or `unknown`. A call made with an idempotency key can be
repeated with the same key: a finished call returns its stored result without paying again, and one still
running is refused with `payment_in_progress`. A key used again for another resource is refused with
`payment_request_invalid`.
