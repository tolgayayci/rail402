This page covers the Rail402 facilitator (`/verify`, `/settle`, `/supported`), the Bazaar catalog and search,
the `upto` settlement contract, the buyer side: the SDK, the `rail402` CLI and the `rail402-mcp` server
that let agents pay, and the [Playground](/playground/overview), a page and server that pay on the testnet
from a browser. For each threat it says what Stellar makes different, which mitigations answer it, where
they live in the code, which tests prove them, and what risk remains.

Every threat is an entry in [`docs/security/threats.json`](https://github.com/tolgayayci/rail402/blob/main/docs/security/threats.json).
The tables below are generated from it, and a unit test fails when a cited source file no longer contains the
cited symbol, when a cited test no longer exists, or when a cited conformance case is not declared by its
harness. The [operational test report](/security/operational-tests) shows the exercises that run these tests
and what they observed.

## Invariants

The design rests on seven properties. Each threat below is an attempt to break one of them.

1. **The facilitator is never the source of payment funds.** It sponsors fees through a fee bump and nothing
   else; any payment that makes a facilitator account a payer, a source or a party to an authorization is
   refused.
2. **A signed authorization moves funds at most once.** The Soroban host consumes its nonce, and Rail402's
   settlement ledger answers every repeat from one record.
3. **The payer's signature fixes the recipient and the amount, or the cap.** Changing either after signing
   fails signature verification on chain.
4. **The sponsor's exposure is bounded** per settlement by the fee ceiling and per hour by the fee budget.
5. **A listing is owned by the `payTo` that was settled,** and is published only after its own origin
   confirms it.
6. **Rail402 and its buyer tools never dial a non-public address** on someone else's behalf, unless loopback
   is explicitly allowed for a local test network.
7. **An agent cannot spend beyond the caps its owner set,** which are checked immediately before signing.

## Replay

A Stellar payment authorization is not a signed transaction but a Soroban authorization entry: a signature
over one contract invocation, a nonce and an expiration ledger, bound to the network by its passphrase. The
host consumes the nonce when the entry is used, so funds can move only once. What remains for the facilitator
is not to pay for duplicates, to give every repeat the same answer, and to stop a seller from serving one
payment many times.

{/* generated:begin topic-replay */}

### R1. The same authorization is settled twice

Mitigated · Tampering, Elevation of privilege · boundary TB2 (Seller and facilitator) · asset: Payer funds

**Threat.** A seller, a buyer or anyone holding a payment sends the same PAYMENT-SIGNATURE to /settle again, one after another or many at once, hoping the payer is charged more than once.

**What Stellar makes different.** An exact or upto authorization is a Soroban authorization entry whose nonce the host consumes when the entry is used; a second use fails on chain with Error(Auth, ExistingValue). The nonce lives under the payer's own address, for G and C accounts alike, until the signature expires. A duplicate that reaches the network is included and fails, so the sponsor still pays its fee.

**Preconditions.** A copy of a payment payload that was already sent to /settle. **Impact.** Without protection: one wasted sponsor fee per duplicate. The payer can never be charged twice, because the host refuses the second use of the nonce.

**Mitigations**

- One settlement record per (network, payer, nonce), claimed before any RPC work; later requests answer from the record instead of submitting. ([`packages/store-postgres/migrations/0001_settlement.sql`](https://github.com/tolgayayci/rail402/blob/main/packages/store-postgres/migrations/0001_settlement.sql), `UNIQUE (network, payer, nonce)`)
- The settle path looks the authorization up first and answers a repeat with the recorded response, marked as a repeat. ([`packages/facilitator/src/engine.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/engine.ts), `answerRepeat`)
- A request whose terms differ from the recorded request is refused, never given the stored success. ([`packages/facilitator/src/fingerprint.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/fingerprint.ts), `requestHash`)
- Verify reads the ledger and refuses an authorization that is being settled or already was. ([`packages/facilitator/src/scheme.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/scheme.ts), `alreadySubmitted`)

**Tests**

- [`packages/facilitator/test/settlement.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/settlement.integration.test.ts): answers a repeated settle with the original result and moves funds once
- [`packages/facilitator/test/settlement.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/settlement.integration.test.ts): settles concurrent duplicates exactly once, all callers getting the same result
- [`apps/rail402/test/idempotency.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/rail402/test/idempotency.integration.test.ts): settles 5 concurrent repeats once: one transfer, one original, identical bodies
- [`apps/rail402/test/idempotency.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/rail402/test/idempotency.integration.test.ts): never answers a request for different terms with the stored success
- [`apps/rail402/test/idempotency.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/rail402/test/idempotency.integration.test.ts): reports a settlement in progress to verify, then the used authorization
- [`packages/facilitator/src/testing.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/testing.ts): grants exactly one claim per authorization, even under concurrency

**Conformance runs.** `live-matrix` case `replay-idempotent`, `live-matrix` case `replay-concurrent`, `live-matrix` case `replay-late`.

**Residual risk.** None for funds. A repeat costs a database read, and rate limits bound how often it can be asked.

### R2. The same authorization in a new envelope

Mitigated · Tampering · boundary TB2 (Seller and facilitator) · asset: Sponsor XLM

**Threat.** An attacker wraps an already settled authorization entry in a transaction of different bytes (another source, sequence or fee) so it is not recognised as a repeat.

**What Stellar makes different.** The authorization is bound to its invocation, not to the transaction, so it can be placed in any envelope. The host refuses the consumed nonce at apply time; a facilitator that only compared envelope bytes would submit it and pay the fee.

**Preconditions.** A copy of a settled authorization entry. **Impact.** One wasted sponsor fee per attempt if it reached the network.

**Mitigations**

- The settlement key is the payer's address and nonce, read from the authorization entry, not the envelope hash. ([`packages/facilitator/src/engine.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/engine.ts), `keyOf`)
- A different envelope for a recorded authorization is refused with the idempotency conflict, naming the recorded transaction. ([`packages/facilitator/src/engine.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/engine.ts), `conflict`)

**Tests**

- [`apps/rail402/test/idempotency.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/rail402/test/idempotency.integration.test.ts): refuses the same authorization in another envelope, naming the recorded transaction
- [`packages/facilitator/test/settlement.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/settlement.integration.test.ts): refuses a settled authorization in a different envelope, and verify names the replay
- [`packages/facilitator/test/state.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/state.test.ts): reports a conflict when the same authorization arrives in a different envelope

**Conformance runs.** `live-matrix` case `replay-rejected`.

**Residual risk.** None: nothing is submitted.

### R3. An authorization replayed on another network

Mitigated · Tampering · boundary TB2 (Seller and facilitator) · asset: Payer funds

**Threat.** A payment signed for stellar:testnet is presented for stellar:pubnet, or the reverse.

**What Stellar makes different.** The signed preimage (HashIdPreimageSorobanAuthorization) includes the network id, the SHA-256 of the network passphrase, so a signature is only valid on the network it was made for.

**Preconditions.** A signed payment for one network. **Impact.** None on chain: signature verification fails on the other network.

**Mitigations**

- The network id is part of every signed preimage the buyer's guard decodes and checks. ([`packages/stellar/src/auth.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/stellar/src/auth.ts), `networkIdForPassphrase`)
- A request is served only on the network its requirements name, and a payload for another network is refused. ([`apps/rail402/src/app.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/rail402/src/app.ts), `invalid_network`)

**Tests**

- [`packages/stellar/test/auth.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/stellar/test/auth.test.ts): is SHA-256 of the passphrase
- [`packages/sdk/test/decide.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/test/decide.test.ts): refuses another network, whether in the preimage or in the requested passphrase
- [`apps/rail402/test/app.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/rail402/test/app.test.ts): refuses networks and schemes it does not serve without calling the core

**Conformance runs.** `rejection-audit` case `unknown-network`.

**Residual risk.** None.

### R4. Paid once, served many times

Accepted risk · Spoofing, Elevation of privilege · boundary TB1 (Buyer and seller) · asset: Seller revenue

**Threat.** A buyer pays once and sends the same PAYMENT-SIGNATURE several times, concurrently or later. A stock upfront seller calls /settle without /verify and serves on success, and an idempotent facilitator answers every repeat with the same success.

**What Stellar makes different.** Nothing Stellar-specific allows it: it follows from answering repeats with the stored result, which the x402 idempotency requirement asks for. The Stellar part is that the answer carries the one settlement transaction hash, which a seller can deduplicate on.

**Preconditions.** A seller that serves on a successful /settle without remembering which settlements it already served. **Impact.** The seller serves a paid resource more than once for one payment. The buyer is charged once.

**Mitigations**

- Every repeated /settle answer carries a repeat marker in EXTENSION-RESPONSES (rail402.settlement.repeat). ([`packages/facilitator/src/responses.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/responses.ts), `markRepeat`)
- The seller helpers refuse a second request whose settlement is a repeat or a transaction already served. ([`packages/sdk/src/seller/dedupe.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/src/seller/dedupe.ts), `withSettleDedupe`)
- In the authorization flow, verify refuses an authorization that is being settled or was. ([`packages/facilitator/src/scheme.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/scheme.ts), `alreadySubmitted`)

**Tests**

- [`apps/rail402/test/app.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/rail402/test/app.test.ts): sends the recorded body and moves the repeat marker into EXTENSION-RESPONSES
- [`packages/sdk/test/seller.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/test/seller.test.ts): trusts Rail402's repeat marker, even for a settlement it never saw
- [`packages/sdk/test/seller.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/test/seller.integration.test.ts): does not serve a replayed payment signature again
- [`packages/sdk/test/seller.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/test/seller.integration.test.ts): serves an upfront settlement once when the facilitator answers its repeat
- [`apps/rail402/test/idempotency.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/rail402/test/idempotency.integration.test.ts): marks the repeat in extension responses, and counts and meters it once

**Conformance runs.** `live-matrix` case `replay-idempotent`.

**Residual risk.** An upfront seller on stock middleware that does not wrap its facilitator client with withSettleDedupe, or deduplicate PAYMENT-RESPONSE.transaction itself, can serve a repeat. The seller helpers page tells upfront sellers to wrap it.

### R5. An upto authorization settled for zero stays usable

Mitigated · Tampering · boundary TB7 (Contracts) · asset: Payer funds

**Threat.** A seller settles an upto payment for zero, then tries to charge the same authorization again for a positive amount.

**What Stellar makes different.** An on-chain zero settlement still uses the payer's authorization entry, so the host consumes its nonce like any other settlement. An off-chain zero (UPTO_ZERO_SETTLEMENT=offchain) sends nothing, so the nonce stays unused on chain until the signature expires.

**Preconditions.** An upto payment settled for zero. **Impact.** Without protection, a second settlement of the same authorization for up to the cap.

**Mitigations**

- The upto contract consumes the payer's nonce for a zero settlement too. ([`contracts/stellar/upto/src/lib.rs`](https://github.com/tolgayayci/rail402/blob/main/contracts/stellar/upto/src/lib.rs), `pub fn settle`)
- An off-chain zero is a terminal record in the settlement ledger, so a later request for any amount is answered from it or refused as a conflict; only the named authority can settle on chain, and it is Rail402's. ([`packages/facilitator/src/upto-scheme.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/upto-scheme.ts), `offchainZero`)

**Tests**

- [`contracts/stellar/upto/src/test/signed.rs`](https://github.com/tolgayayci/rail402/blob/main/contracts/stellar/upto/src/test/signed.rs): a_zero_settlement_also_consumes_the_nonce
- [`packages/facilitator/test/upto.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/upto.integration.test.ts): settles zero on-chain: the nonce is consumed and no funds move
- [`packages/facilitator/test/upto.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/upto.integration.test.ts): settles zero off-chain when configured: no transaction, the authorization used up in the ledger
- [`packages/facilitator/src/testing.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/testing.ts): finishes an upto zero-amount success without an envelope, only for the claim's owner

**Conformance runs.** `live-matrix` case `upto-zero`.

**Residual risk.** With off-chain zeros and STORE=memory, a restart forgets the record; the authorization then stays settleable by Rail402's own authority until it expires. Use Postgres wherever off-chain zeros are enabled.

## Front-running

Because the authorization is bound to its invocation rather than to a transaction, anyone who sees it before it
lands can submit it in a transaction of their own. That can only make the signed payment happen, exactly as
signed; it cannot redirect it. The cost is Rail402's own failed transaction, and the risk is telling a seller
"failed" for a payment that settled.

{/* generated:begin topic-front-running */}

### F1. A copied exact authorization lands first

Accepted risk · Denial of service · boundary TB3 (Facilitator and Stellar) · asset: Sponsor XLM

**Threat.** Someone who sees the settlement envelope (the seller, an RPC operator, a validator's pending queue) copies the payer's authorization entry into a transaction of their own and gets it included before Rail402's.

**What Stellar makes different.** A Soroban authorization is a bearer instrument for exactly one invocation: whoever submits it can only make the signed transfer happen, from the payer to payTo for the signed amount. It cannot be redirected. Rail402's own transaction then fails on the consumed nonce and its fee is spent.

**Preconditions.** Access to the envelope between signing and inclusion, and an account to pay the copy's fee. **Impact.** One wasted sponsor fee per event. The attacker pays its own fee and gains nothing; the payment settles as signed.

**Mitigations**

- Rail402 submits as soon as the settle-time simulation passes, which leaves little time to copy the entry. ([`packages/facilitator/src/engine.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/engine.ts), `execute`)

### F5. A payload holder fixes the upto amount through the facilitator's /settle

## Fee sponsorship

The sponsor pays the fee of every transaction it submits, and Soroban charges resource fees whether the
transaction succeeds or fails. Every refusal Rail402 can make before signing costs nothing; a transaction that
is included and fails costs its fee. Rail402 refuses whatever it can see coming, names and counts what it
cannot, and bounds the total.

{/* generated:begin topic-fee-sponsorship */}

### S1. A payment passes simulation and fails at apply

Accepted risk · Denial of service · boundary TB3 (Facilitator and Stellar) · asset: Sponsor XLM

**Threat.** A payer spends the balance, or changes a smart account's state, after the settle-time simulation and before inclusion, so the settlement is included and fails.

**What Stellar makes different.** Soroban resource fees are charged when a transaction is included, success or failure; the sponsor pays through the fee bump. Simulation runs against the latest ledger, so a change made in the ledgers between simulation and inclusion is not seen.

**Preconditions.** A payer (or its smart-account policy) able to act within about one ledger of the settlement. **Impact.** One wasted sponsor fee per event, never more than the fee ceiling. No funds move.

**Mitigations**

- Settle simulates again with the current ledger, so a change made before settle is refused without submitting. ([`packages/facilitator/src/scheme.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/scheme.ts), `settle`)
- The failure is named from the transaction's diagnostic events and counted as wasted fee. ([`packages/facilitator/src/explain.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/explain.ts), `explainFailedTransaction`)
- The hourly fee budget and the reserve floor bound the total a griefer can burn. ([`packages/facilitator/src/guard.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/guard.ts), `SponsorBudget`)

## Catalog poisoning

The Bazaar catalogs resources automatically after a successful settlement. The settlement proves one thing,
that a payment reached `payTo`; everything else in the resource description came from the buyer's request and
must be confirmed at the resource's own origin before it is published.

{/* generated:begin topic-catalog-poisoning */}

### P1. Forged listing metadata or price

Mitigated · Spoofing, Tampering · boundary TB2 (Seller and facilitator) · asset: Catalog and search integrity

**Threat.** A buyer (or a seller's buggy client) echoes a resource block with a false description, price or schema in the payment, hoping the catalog publishes it.

**What Stellar makes different.** Nothing on chain describes the resource; the settlement proves only that a payment to payTo happened. The metadata must be confirmed at its origin.

**Preconditions.** One real settlement to the seller. **Impact.** Misleading listings shown to buyers and agents.

**Mitigations**

- An HTTP resource, or an MCP tool at an http(s) endpoint, is published only after its own 402 (for a tool, the answer to an unpaid tools/call over MCP) confirms payTo, price and metadata; what is published always comes from that answer, so echoed metadata never changes a listing on its own. ### P2. Taking over another seller's listing

**Threat.** An attacker pays a URL that belongs to another seller, but to its own payTo, to take over or modify that listing.

## Smart accounts

A `C…` payer is a contract account whose `__check_auth` decides whether a payment is authorized. Nothing about
it can be checked offline: only executing it tells, and its answer can change between simulation and
inclusion. Rail402 simulates in enforcing mode at verify and again at settle; policy composition with `upto`
is proved in contract tests with OpenZeppelin smart accounts.

{/* generated:begin topic-smart-accounts */}

### A1. A payment signed by a key the account does not accept

Mitigated · Spoofing · boundary TB7 (Contracts) · asset: Payer funds

**Threat.** Someone signs a C-account payment with a key that is not one of the smart account's signers.

**What Stellar makes different.** A contract account authorizes through its own \_\_check_auth; only executing it can tell whether a signature is valid. There is no signature a facilitator could check offline.

**Preconditions.** Knowledge of the smart account's address. **Impact.** None if detected; the account's \_\_check_auth refuses.

**Mitigations**

- Verify and settle both run an enforcing simulation, which executes \_\_check_auth; a refusal is named smart_account_rejected. ([`packages/stellar/src/diagnostics.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/stellar/src/diagnostics.ts), `classifyTransferFailure`)

**Tests**

- [`packages/facilitator/test/settlement.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/settlement.integration.test.ts): rejects a smart-account payment signed by the wrong key
- [`packages/stellar/test/diagnostics.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/stellar/test/diagnostics.test.ts): a smart-account payer rejecting in \_\_check_auth → smart_account_rejected
- [`packages/upto/test/facilitator.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/upto/test/facilitator.test.ts): attributes refusals inside a smart account's \_\_check_auth to the account

**Conformance runs.** `live-matrix` case `c-payer-wrong-key`, `rejection-audit` case `upto-c-payer-wrong-key`.

**Residual risk.** None.

### A2. \_\_check_auth that passes simulation and fails at apply

Accepted risk · Denial of service · boundary TB7 (Contracts) · asset: Sponsor XLM

**Threat.** A smart account whose \_\_check_auth depends on state it can change (a nonce, a time, a policy budget) passes simulation and fails at inclusion, deliberately.

**What Stellar makes different.** \_\_check_auth is arbitrary contract code. Its result at apply time can differ from simulation, and the included, failed transaction's fee is the sponsor's.

**Preconditions.** A smart account the attacker controls. **Impact.** One wasted sponsor fee per payment.

**Mitigations**

- The simulation is repeated at settle, so state changed before settle is caught. ([`packages/facilitator/src/scheme.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/scheme.ts), `settle`)
- Wasted fees are metered; the hourly budget bounds the total. ([`packages/facilitator/src/guard.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/src/guard.ts), `SponsorBudget`)

**Tests**

- [`packages/facilitator/test/fee-exposure.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/fee-exposure.integration.test.ts): names a smart account whose \_\_check_auth passes the settle-time simulation and fails at inclusion; the fee is counted as wasted
- [`packages/facilitator/test/fee-exposure.integration.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/facilitator/test/fee-exposure.integration.test.ts): stops settling once the hourly fee budget is committed, before any RPC work

**Residual risk.** Like S1, the race within one ledger cannot be closed. A per-payer limit on on-chain failures is not built; the hourly budget is the bound.

### A3. Policy events refuse exact payments from policy accounts

Accepted risk · Denial of service · boundary TB7 (Contracts) · asset: Availability

**Threat.** A smart account with a policy that emits its own events (such as a spending limit recording a spend) pays with exact.

**What Stellar makes different.** The upstream @x402/stellar exact verifier accepts only the token's transfer event in the simulation and refuses any other contract event as invalid_exact_stellar_payload_event_not_transfer. The upto verifier accepts events other than balance changes, so policy events do not refuse upto payments.

**Preconditions.** A payer whose \_\_check_auth publishes events. **Impact.** Such accounts cannot pay with exact through any facilitator built on the upstream verifier; nothing moves and the sponsor pays nothing.

**Mitigations**

- The refusal is passed through with its registered code and reason. ([`packages/stellar/src/codes.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/stellar/src/codes.ts), `invalid_exact_stellar_payload_event_not_transfer`)
- upto accepts non-balance events such as a policy's own. ([`packages/upto/src/facilitator/simulation.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/upto/src/facilitator/simulation.ts), `checkSimulationEvents`)

**Tests.** None: this is a documented limit, not a behaviour Rail402 implements.

**Residual risk.** An upstream limit of the exact scheme; it fails closed. Policy accounts pay with upto.

### A4. A spending limit that does not cover upto

### A5. Bypassing the policy through the Default rule

Mitigated · Elevation of privilege · boundary TB7 (Contracts) · asset: Agent budgets

**Threat.** An agent key picks a context rule without the spending policy (the Default rule, or the policy-free upto rule for the approve), or a relayer moves a signed payment to another rule.

### A6. Concurrent payments beyond the account's own budget

Accepted risk · Denial of service · boundary TB7 (Contracts) · asset: Sponsor XLM

**Threat.** Several payments from one policy account are verified at once; together they exceed the account's budget, and the later ones fail at apply.

## MCP paid calls

`rail402-mcp`, the SDK and the CLI hold a signing key on the agent's side. The threats are about the agent's
money: paying more than allowed, paying the wrong party, leaking the key, paying twice, and following URLs it
should not.

### M1. An agent spends beyond its caps

Mitigated · Elevation of privilege · boundary TB6 (Agent, MCP server and paid URLs) · asset: Agent budgets

**Threat.** A model, a prompt injection or a bug makes an agent pay more per call or per session than its owner allowed, including through many concurrent calls or several processes.

**What Stellar makes different.** A signed authorization is spendable by whoever holds it until it expires, so the cap must be enforced before signing, not after.

**Preconditions.** An agent with a signing key and a budget. **Impact.** Loss of the agent owner's funds up to the key's balance.

**Mitigations**

### M2. Payments on networks, assets or to recipients not allowed

**Preconditions.** A seller offering unexpected terms. **Impact.** Payment in the wrong asset or to the wrong party.

**Mitigations**

### M3. Secrets in tool schemas, results, errors or logs

Mitigated · Information disclosure · boundary TB6 (Agent, MCP server and paid URLs) · asset: Secrets

**Threat.** The signing seed, its raw bytes, a signature or a payment header leaks into an MCP tool schema, a tool result, a protocol error, a log line, the budget ledger or the CLI's output.

**What Stellar makes different.** A Stellar seed (S…) or its 32 raw bytes is the whole key; a leaked signed authorization is spendable until it expires.

**Preconditions.** Any error or log path that echoes inputs, or a seller that echoes the payment into its answer. **Impact.** Loss of the agent's funds.

### M6. A tampered payment or a false settlement report

Mitigated · Tampering, Repudiation · boundary TB6 (Agent, MCP server and paid URLs) · asset: Agent budgets

**Threat.** A scheme client changes the payload after the guard approved it, or a seller reports a settlement that did not happen, reports another payment's transaction hash, or settles through its own contract so the transaction does not look like a direct settlement.

**What Stellar makes different.** The host records every authorization nonce it consumes in a temporary ledger entry keyed by the payer and the nonce, and only the entry the payer signed can consume it. A transaction used a payment's authorization exactly when it carries the payer's entry with that payment's nonce and its meta creates that nonce entry, whatever its call path: Soroban matches an entry below the top-level call, so a wrapper, router or batch contract can settle it too, and one transaction can consume several nonces. A transfer event alone says nothing about which authorization moved the money.

**Preconditions.** A malicious scheme client or seller. **Impact.** Paying for something else, believing a payment failed or succeeded wrongly, or a session budget that under-counts what moved.

**Mitigations**

- The guard compares the payload with what it signed. ([`packages/sdk/src/policy/guard.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/src/policy/guard.ts), `checkGuardedPayload`)
- A payment is proven only by its own nonce: a transaction that consumed it settles the reservation whatever its shape, for the exact price, or for upto the amount the signed settlement contract recorded for the signed terms (the whole cap when that cannot be read). A consumed authorization is never released. ([`packages/sdk/src/policy/proof.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/src/policy/proof.ts), `reservationSettlement`)
- A reported hash is only a claim against the payment it was reported for and counts as spent; it never removes a transaction from another payment's proof. Budget returns only when the authorization has expired and no transaction in its validity range consumed it. ([`packages/sdk/src/policy/reconcile.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/src/policy/reconcile.ts), `reconcile`)
- An expired payment the RPC can no longer prove either way counts as spent at its whole amount and is no longer reconciled. ([`packages/sdk/src/sqlite/ledger.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/src/sqlite/ledger.ts), `markUnprovable`)

**Tests**

## The upto contract

With `upto` the payer signs a cap, and the settlement authority named in the terms chooses the amount at
settlement. The contract `x402-upto-stellar` has no admin, no storage and no upgrade path; the payer's
signature covers the terms and an `approve` of the cap to the contract, and the authority's authorization

**What Stellar makes different.** /verify simulates the settlement for the full cap, so the signature, balance and trustline hold at that moment, but a Soroban authorization is not an escrow: nothing is locked until the settlement transaction applies.

**Preconditions.** A buyer willing to default, and a seller that releases output before its own settlement succeeds. **Impact.** One request served unpaid. A streaming or metered seller cannot withhold what it already sent.

**Mitigations**

- Short maxTimeoutSeconds, settling immediately after serving, withholding buffered output until settlement succeeds (the stock Express middleware does), and refusing payers whose settlements fail. ([`docs/facilitator/upto.mdx`](https://github.com/tolgayayci/rail402/blob/main/docs/facilitator/upto.mdx), `Payment is not guaranteed after verification`)

**Tests.** None: this is a documented limit, not a behaviour Rail402 implements.

**Residual risk.** Accepted: upto is post-paid by design; the loss is bounded by one request's cap.

## Operations

Mitigated · Denial of service, Repudiation · boundary TB4 (Facilitator and its state) · asset: Payer funds

**Threat.** The process dies after signing or broadcasting a settlement and before recording its outcome; a restart submits a replacement and the payer is charged twice, or the seller is never told.

## The Playground

site or a seller could do with either.

{/* generated:begin topic-playground */}

### PG1. The relay used to reach private networks or as an open proxy

Mitigated · Spoofing, Information disclosure, Denial of service · boundary TB8 (Playground page and server) · asset: Operator infrastructure

**Threat.** A visitor, or a script calling the Playground's API, asks the relay to fetch a loopback, private or cloud-metadata address, a name that resolves to one, or a seller that redirects to one; or uses the relay to send volume to third parties from the Playground's address.

**What Stellar makes different.** Nothing Stellar-specific: the relay exists because Rail402 and most x402 sellers answer no CORS headers, so a page cannot call them itself. A paid request through it carries a PAYMENT-SIGNATURE the visitor's own key made.

**Preconditions.** Network access to the Playground server. **Impact.** Without protection: requests into the server's network, or the Playground's address used for abuse.

**Mitigations**

- The relay sends with safe-fetch under a fixed policy: https on port 443 to public addresses only, DNS answers checked and pinned, redirects refused except same-origin hops for unpaid probes, request and answer size limits. ([`apps/playground/src/relay/egress.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/src/relay/egress.ts), `RelayEgress`)
- By host name, it never contacts the Playground itself (its public host and the platform's generated domain), the facilitator, the Bazaar or an operator-denied host. ([`apps/playground/src/relay/egress.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/src/relay/egress.ts), `playground_relay_loop`)
- Per-client, global, per-host, in-flight and daily byte limits, with Retry-After, and a switch to turn the relay off. ([`apps/playground/src/limits.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/src/limits.ts), `DailyBudget`)
- Global limits are fair-shared: one network (an IPv4 address or an IPv6 /48) holds at most an eighth of a pool, or its per-client limit when that is larger; clients are keyed by IPv4 address or IPv6 /56. ([`apps/playground/src/limits.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/src/limits.ts), `SharedRate`)
- Only a payment that decodes as an x402 payment counts against the paid limits, whether it travels in PAYMENT-SIGNATURE or in an MCP tool call's \_meta; anything else is refused before a token is taken. - The demo seller has a paid pool of its own, a paid request that reached no seller gives the shared pool its token back, and the lab sellers return it when the facilitator was never asked, so payments that only have the right shape cannot use up the pools the demo flows need. - Unpaid requests wait no longer than the SDK's probe timeouts; bodies pass only as JSON, text or octet-stream; slots of an abandoned upload or an unread answer are released; connections to hosts other than the demo seller are closed after each answer. ([`apps/playground/src/relay/relay.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/src/relay/relay.ts), `timeoutsFor`)

### PG2. Another site drives the relay from a visitor's browser

Mitigated · Spoofing, Information disclosure · boundary TB8 (Playground page and server) · asset: Operator infrastructure

**Threat.** A page on another origin makes a visitor's browser send requests through the Playground's relay, seller check or proxies, or reads their answers.

**What Stellar makes different.** The relay holds no key and no session, so a forged request carries no authority the attacker lacks; a payment needs a signature from the key in the Playground's own page.

**Preconditions.** A visitor with the Playground open, or not, visits the attacker's page. **Impact.** Without protection: the Playground's relay used through visitors' browsers.

**Mitigations**

- The relay needs its own request headers, which a cross-site form cannot set; a browser's Sec-Fetch-Site must be same-origin and its Origin the Playground's public origin. ([`apps/playground/src/security.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/src/security.ts), `sameOrigin`)
- The relay answers no CORS headers, so no other origin can read an answer. ([`apps/playground/src/shared/relay-protocol.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/src/shared/relay-protocol.ts), `x-relay-target`)
- The Bazaar and /supported proxies refuse another site's requests the same way, so no page can spend their shared upstream budget through visitors' browsers. ([`apps/playground/src/proxy/bazaar.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/src/proxy/bazaar.ts), `proxyOrigin`)

**Tests**

- [`apps/playground/test/relay.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/test/relay.test.ts): answers only same-origin requests from the page
- [`apps/playground/test/seller-check.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/test/seller-check.test.ts): answers only same-origin requests from the page
- [`apps/playground/test/proxy.test.ts`](https://github.com/tolgayayci/rail402/blob/main/apps/playground/test/proxy.test.ts): refuses requests another site's page makes, before any upstream fetch

**Residual risk.** Clients that are not browsers send neither header and pass. They get nothing a browser visitor lacks, but they can use the relay as an https egress at the Playground's address, bounded only by the limits (PG1).

### PG3. Script injected into the page uses the testnet key
