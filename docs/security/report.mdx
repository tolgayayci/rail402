This report records what has been reviewed in Rail402, what each review found, and how every finding
was resolved. Each finding is an entry in
[`docs/security/findings.json`](https://github.com/tolgayayci/rail402/blob/main/docs/security/findings.json).
A unit test fails when a finding has no severity or status, when a fixed finding has no fix commit on
`main` or no regression test that still exists, when an accepted finding has no written acceptance, or
when a critical or high finding is accepted rather than fixed. The release workflow refuses to publish a
version tag while a critical or high finding is open or accepted.

No release has been frozen for an external review yet. The findings below come from internal reviews of
the code that shipped in the npm packages listed above. Several were found and fixed before the affected
component was first released; for those, the fix commit is the commit that introduced the component.

## Scope and method

Each internal review read the code and the tests of the components in its scope, tried to break the
invariants of the [threat model](/security/threat-model) with probes against a local network and the
public testnet, and recorded every finding with a severity:

- **Critical**: funds can be lost or stolen, or the facilitator becomes a source of funds.
- **High**: a stated security property does not hold, for example an agent can spend beyond its cap.
- **Medium**: a property holds only partly, or a wrong outcome is reported for a payment.
- **Low**: a defect with a narrow precondition or a bounded cost.
- **Info**: a note without a defect in Rail402.

A finding is closed by a fix with a regression test, or, for a medium, low or info finding, by a written
acceptance that names the mitigations and the role that approved it.

### F-2026-001

**The buyer budget could release an upto remainder without proof**

High · sdk · Fixed · found by `REV-2026-09-internal-1` on 2026-09-30, resolved 2026-09-30 · threats M1

Budget reconciliation released the unspent part of an upto cap as soon as any transfer from the payer to the recipient at or below the cap appeared on chain, without proving that the transfer came from that authorization. A seller could make a session under-count what it spent and so exceed the session cap. Reconciliation now counts a payment only from a transfer made with the payment's own authorization, proven by the payer's consumed nonce.

**Fixed in** [`c00699b`](https://github.com/tolgayayci/rail402/commit/c00699bbf0984ea49918d84ee91a81d586f625a1). **Tests**

- [`packages/sdk/test/reconcile.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/test/reconcile.test.ts): settles a payment only from a transfer made with its own authorization
- [`packages/sdk/test/reconcile.test.ts`](https://github.com/tolgayayci/rail402/blob/main/packages/sdk/test/reconcile.test.ts): keeps an upto remainder pending until the chain shows what moved

**The deploy gate accepted an image built for the tag name from another commit**

Medium · operations · Fixed · found by `REV-2026-10-prelaunch` on 2026-10-28, resolved 2026-10-29 · threats C2, C3

The deploy gate checked that the release tag was signed and that each image's attestation came from the release workflow run for that tag name, but not that the build ran from the signed commit. Someone able to push a tag but without a release-signing key could point the tag at a commit whose own release.yml built and attested an image, then let the signed tag replace it; the gate would accept that image for the signed commit. The gate now requires each attestation to name the signed commit both as the build's source and as the workflow file that ran (--source-digest, --signer-digest).
