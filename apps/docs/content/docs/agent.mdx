## Paying for an endpoint you already know

Stock client. Nothing from us.

```ts
import { x402Client } from "@x402/core/client";
import { wrapFetchWithPayment } from "@x402/fetch";
import { createEd25519Signer } from "@x402/stellar";
import { ExactStellarScheme } from "@x402/stellar/exact/client";

const client = new x402Client();
client.register("stellar:*", new ExactStellarScheme(createEd25519Signer(SECRET, "stellar:testnet")));

const res = await wrapFetchWithPayment(fetch, client)("https://api.example.com/premium/quote?symbol=XLM");
```

That is the whole flow: 402 → sign an auth entry → retry → 200. The buyer needs **no XLM** — the
facilitator sponsors the fee.

> **If you hand-roll the transaction instead of using the client:** the transfer's `from` must not
> also be the transaction source. When it is, Soroban satisfies `require_auth` with
> source-account credentials, and the `exact` scheme accepts only address credentials — you will get
> `invalid_exact_stellar_payload_unsupported_credential_type`. The stock client handles this. This
> cost us a debugging cycle.

## Paying with a spend cap

`@x402-stellar/agent-helpers` adds the safety an autonomous buyer needs.

```ts
import { payAndFetch } from "@x402-stellar/agent-helpers";

const result = await payAndFetch(
  { bazaarUrl: "https://<facilitator>", stellarSecret: SECRET, network: "stellar:testnet" },
  "https://api.example.com/premium/quote",
  { maxAmount: "5000000", queryParams: { symbol: "XLM" } },   // required, no default
);

if (!result.ok) console.error(result.error.code, result.error.reason);
else console.log(result.data.body, result.data.paid.transaction);
```

`maxAmount` is **required and has no default** — a default would make an unbounded spender by
omission. The price is read from an **unpaid probe first**, so an over-budget resource costs one HTTP
request and zero money:

```
mcp_budget_exceeded
"This resource costs 5000000 atomic units of CBIE… on stellar:testnet,
 which exceeds your maxAmount of 1000000. No payment was made."
```

All budget maths is bigint. `Number("9007199254740993")` silently becomes `…992`, and that is the one
comparison that decides whether money moves.

## Finding something you have never seen

```ts
import { searchBazaar, discoverAndPay } from "@x402-stellar/agent-helpers";

const found = await searchBazaar(config, "current price of a commodity by ticker", { limit: 5 });
// → resource, description, price, inputSchema, usage { uniquePayers }

const result = await discoverAndPay(config, "translate text to spanish", { maxAmount: "1000000" });
```

`discoverAndPay` is the whole loop in one call: search → pick the best match → pay. A search that
matches nothing costs nothing.

Results carry `inputSchema`, so an agent learns **how to call** an endpoint it has never seen. They
also carry `usage.uniquePayers` — a count of distinct settled payers, which is expensive to forge
because every one is a real on-chain payment.

## From inside an agent runtime (MCP)

Two tools, strict schemas both ways:

| Tool | Does |
|---|---|
| `search_stellar_resources` | Natural-language search. Pays nothing. |
| `pay_and_call` | Discover → pay → retry. Requires `maxAmount`. |

```json
{
  "mcpServers": {
    "x402-stellar": {
      "command": "node",
      "args": ["/path/to/apps/mcp-discovery/dist/index.js"],
      "env": {
        "BAZAAR_URL": "https://<facilitator>",
        "CLIENT_STELLAR_PRIVATE_KEY": "S...",
        "MAX_AMOUNT_CEILING": "10000000"
      }
    }
  }
}
```

`MAX_AMOUNT_CEILING` is an operator limit that overrides whatever the agent asks for — worth setting.

## Handling failure

Every rejection is `{ code, reason, retryable }`. Branch on `code`; never parse `reason`.

| Code | Meaning | Retry? |
|---|---|---|
| `mcp_budget_exceeded` | Price above your cap. **Nothing was paid.** | No — raise the cap or move on |
| `invalid_exact_stellar_payload_missing_trustline_recipient` | **The seller** cannot receive the asset | No — not your fault, report it |
| `invalid_exact_stellar_payload_missing_trustline_payer` | You cannot hold the asset | No — add a trustline |
| `invalid_exact_stellar_payload_insufficient_balance` | You are short | No — fund up |
| `invalid_exact_stellar_payload_authorization_replayed` | Payload already used | No — sign fresh |
| `settle_exact_stellar_transaction_submission_failed` | Network trouble | **Yes** |

`retryable` is meaningful: a replayed authorization is never retryable, and retrying it just wastes
requests.

## Getting testnet funds

You need a funded account with a trustline to the asset you will pay in.

1. [Stellar Lab](https://lab.stellar.org/account/create) → generate → fund with friendbot
2. Add a USDC trustline → testnet USDC from the [Circle faucet](https://faucet.circle.com/)

Or run `examples/paid-api-agent/src/setup.ts`, which issues its own asset and funds everything from
friendbot — no faucet at all.

## Checklist

- [ ] `maxAmount` set on every paid call, from a real budget
- [ ] `MAX_AMOUNT_CEILING` set if running unattended
- [ ] Branch on `error.code`, never on message text
- [ ] Respect `retryable` — do not retry a replay or a budget refusal
- [ ] Buyer account funded, with a trustline to the payment asset
