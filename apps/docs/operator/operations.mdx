## Throughput under burst traffic

One Stellar account settles about one transaction per ledger, which is roughly five seconds. Agent traffic is bursty, so add signing accounts rather than replicas:

```bash
FACILITATOR_STELLAR_CHANNEL_SECRETS=S...,S...,S...    # independent accounts, used round-robin
FACILITATOR_STELLAR_FEE_BUMP_SECRET=S...              # pays fees, freeing the settling accounts' sequence numbers
```

Fund every channel account. The facilitator rejects duplicate secrets at startup, because they share a sequence number and add no capacity. A fee-bump account decouples fee payment from settlement, so a settling account never waits on a fee.

## Monitoring

`/metrics` exposes Prometheus counters with no per-caller dimension. The one to watch is `x402_rejections_total{code}`. A spike in a single code names the problem without reading logs. You also get verify and settle counts by outcome, catalog size, uptime, and discovery-search signals.

Wire `/health` to your orchestrator. It returns HTTP 200 with a JSON body, and reports `status: "degraded"` when catalog writes are failing while the service keeps serving from memory. Scrape `/metrics` for trends.

Alert thresholds and incident procedures are part of the operator guide.

## Self-facilitation

Run verify and settle in-process, with no external facilitator and no network hop, when you sell your own services:

```ts
import { buildFacilitator, loadConfig } from "@rail402.dev/facilitator";
import { x402ResourceServer } from "@x402/core/server";

const { facilitator } = buildFacilitator(loadConfig(process.env));

// Adapt the in-process facilitator to the client interface the resource server expects.
// verify and settle already return promises; getSupported answers synchronously, so wrap that one.
const localFacilitator = {
  verify: facilitator.verify.bind(facilitator),
  settle: facilitator.settle.bind(facilitator),
  getSupported: async () => facilitator.getSupported(),
};

const server = new x402ResourceServer([localFacilitator]); // no HTTP hop, no third party
```

This keeps the whole payment path inside your process. The `@rail402.dev/facilitator` package ships in the repository.

## Verify your deployment

Acceptance is tested at the wire level. Point the upstream x402 end-to-end suite at your deployment, which tests your facilitator with stock SDK code rather than your own assertions:

```bash
pnpm --filter @rail402.dev/conformance install-proxy
X402_STELLAR_FACILITATOR_URL=https://your-deployment.example pnpm --filter @rail402.dev/conformance run
```

The `dual` run additionally runs the suite at the latest upstream `main`, so you can tell a regression in your deployment apart from a change in the spec. See `packages/conformance` in the repository for the harness and its prerequisites.

The spec moves, roughly one change affecting a Stellar facilitator every few weeks, almost always additive. The pinned spec commits are diffed against upstream regularly, so updates land before a stock client notices.

## Appear on the Explorer

Set `FACILITATOR_PUBLIC_URL` to your deployment's public base URL. A built-in heartbeat announces the deployment to the [Rail402 Explorer](/explorer/overview), which then attributes your settlements to you and re-polls your `/supported` for signer changes. The announcement is a lead, not a claim: the Explorer probes your `/supported` itself and registers only what it verifies. Set `EXPLORER_ANNOUNCE_URL=""` to opt out.
