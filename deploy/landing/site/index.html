With Rail402 the API just names its price, and your code pays for that one answer.

02How it works

Ask, pay, get the answer. In one round trip.

The web has had a "402 Payment Required" code since 1997 that nobody could use. x402 is the open standard that does. Rail402 is the facilitator in the middle: it checks the payment, sends it to Stellar and pays the fee.

  • The buyer signs once. Change the amount or the receiver and the signature breaks.
  • The money goes straight from buyer to seller. Rail402 never holds it.
  • Every refusal comes back with a clear code and a reason.

04Stellar-native

Made for Stellar, not ported to it.

A payment is a Soroban token transfer. The buyer signs one authorization that names the token, the receiver and the amount, and nothing else can be changed without breaking it. Rail402 puts it on the ledger from its own accounts and pays the fee.

  • Classic G… wallets and C… smart accounts both pay. A smart account runs its own checks.
  • Circle USDC by default, or any SEP-41 token, with 6, 7 or 18 decimals.
  • A pool of channel accounts settles many payments side by side.

06Built by Rail402

We wrote upto for Stellar.

x402 started with fixed prices. Rail402 wrote the Stellar version of upto, the metered scheme: the specification, the Soroban contract that enforces it, and the code for buyers, sellers and facilitators. It is proposed to the x402 project upstream.

  • The buyer signs a cap and a deadline. The contract checks the amount is between zero and the cap.
  • Each signature settles once and expires with the payment window. The unused part never leaves the wallet.
  • The contract has no admin, can't be changed and stores nothing. Its source is verified on chain.

11Agent budgets

Give every agent a wallet with rules.

An agent can pay from a plain key, or from a smart account with a budget written into it. Then the account itself refuses anything over the limit, so even a leaked agent key can't spend more than you allowed.

  • Payments inside the budget settle as usual.
  • A payment over what's left is refused, and nothing moves.
  • The agent's key can't switch to a rule without the budget.

Works with OpenZeppelin smart accounts. Our budget policy is an example in the repository, proven by tests on testnet.

15Clear refusals

Every "no" comes with a reason.

When Rail402 refuses something, it never just says "error". Each code has a fixed name, an HTTP status, a plain reason and a flag that says whether trying again can work. Tests pin all of them, so your code can rely on them.

  • Branch on the code. Show the reason to people.
  • A reason can never be empty.
  • A code never changes without a changelog entry.

16Run it your way

Use ours, or run your own.

The same facilitator runs in three ways. Your sellers and buyers don't notice the difference: they only see a URL.

hosted

Point at our URL

Nothing to run. Free on testnet; mainnet with an API key.

https://testnet.rail402.dev
https://mainnet.rail402.dev
docker

Your own server

One command builds the image, funds a testnet sponsor and starts Postgres and the service. 

$ ./deploy/docker.sh
in-process

Inside your app

Import the facilitator into your own Node server. No network hop.

$ npm i @rail402.dev/facilitator

Whichever you pick, you get

You choose what it accepts

Turn testnet and mainnet on or off, and list the tokens you take. USDC is the default.

You set the limits

Fees, rate limits and per-key quotas are settings, never fixed in the code.

Mainnet won't start half-set

If a mainnet setting is missing or unsafe, the service refuses to start instead of guessing.

Keys stay in files

Secret keys are read from files on your machine, not pasted into settings or logs.

Easy to watch

Built-in health, readiness and metrics pages for your monitoring.
